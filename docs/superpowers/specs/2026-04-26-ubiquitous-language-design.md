# Ubiquitous Language Skill — Design

> Status: Draft for plan
> Date: 2026-04-26
> Inspired by: [matt-pocock/skills/ubiquitous-language](https://github.com/mattpocock/skills/blob/main/ubiquitous-language/SKILL.md)

## Goal

Add a `/jlu-ubiquitous-language` command (and supporting agents) that discovers, curates, and persists the domain terminology of the workspace into a single canonical glossary. The glossary lives at the workspace level, draws from three sources (code, user interview, spec/conversation artifacts), and is refined through a review-then-save loop driven by free-text user feedback.

The skill aims to give every spec, proposal, and code change a shared vocabulary, with each term anchored to the services where it's implemented and referenced.

## Constraints (decided during brainstorm)

| Decision | Choice |
|----------|--------|
| Sources of terminology | Hybrid: code scan + user interview + spec/conversation artifacts |
| Glossary scope | Workspace-wide only — single canonical file |
| Invocation | Standalone command + auto-hooks in both `/jlu-map-codebase` and `/jlu-new-task` |
| Hook aggressiveness | Tiered: map-codebase appends candidates; new-task consults read-only |
| Output structure | Term tables + relationships + service locations + ambiguity log (custom — no example-dialogue section) |
| Architecture | Two-agent split: extractor (code-only) + curator (interview + draft + review loop) |
| Review gate | Standalone command always shows a draft; user approves, requests changes, or cancels — only "approve" overwrites canonical |

Workspace artifacts (in target project's `.spec-workspace/`):

```
.spec-workspace/
└── glossary/
    ├── UBIQUITOUS_LANGUAGE.md                    # canonical, only via review-gate approval
    ├── UBIQUITOUS_LANGUAGE.draft.md              # transient — written by curator, deleted on approve/cancel
    ├── candidates.json                           # sidecar — appended by extractor
    └── .last-curation.json                       # marker — per-service commit map of last curation
```

A separate `glossary/` directory keeps workspace-wide artifacts out of `services/<id>/codebase/` (per-service) and `specs/` (per-task). The candidates sidecar is machine state — the user never edits it directly; it's the bridge between unattended hooks and the next interactive curation.

## Artifact Schemas

### `UBIQUITOUS_LANGUAGE.md` (canonical)

```markdown
# Ubiquitous Language

> Generated by `/jlu-ubiquitous-language` on <date>. Last curation: <commit-list>.
> This is the canonical glossary for the workspace. Use these terms in specs, code, and discussions.

## Terms

### Domain: <subdomain-name>

| Term | Definition | Aliases to avoid |
|------|------------|------------------|
| <TermName> | <one-sentence definition> | <Alias1>, <Alias2> |

### Domain: <other-subdomain>
...

## Relationships

- A **<TermA>** has many **<TermB>**.
- A **<TermB>** is composed of one or more **<TermC>**.

## Service Locations

| Term | Implemented in | Also referenced by |
|------|----------------|---------------------|
| <TermName> | `<service>` (`src/<...>`) | `<other-service>` (`src/<...>`) |

## Ambiguity Log

> Conflicts surfaced during curation and how they were resolved.

- **<date>** — `<TermA>` vs `<TermB>`: <one-line description of conflict>. Canonical: `<chosen>`. <other> added to aliases-to-avoid.
```

Notes:

- Subdomains (`### Domain: …`) are emergent — curator clusters terms by service/module co-occurrence, asks the user for a name only if clustering is ambiguous.
- "Implemented in" = primary owner (where the symbol/table/index is *defined*). "Also referenced by" = consumers (imports, HTTP calls, event handlers, schema usage).
- Definitions are one sentence. Multi-sentence definitions are a smell — split into multiple terms.
- Examples in this schema are placeholders; the curator never invents domain content.

### `candidates.json` (extractor sidecar)

```json
{
  "version": 1,
  "updated_at": "<ISO datetime>",
  "candidates": [
    {
      "term": "<TermName>",
      "first_seen_commit": "<sha>",
      "first_seen_at": "<ISO datetime>",
      "discovered_in_services": ["<service-id>", "..."],
      "evidence": [
        {"service": "<service-id>", "path": "src/<...>", "kind": "<entity-class|table-definition|controller|...>"}
      ],
      "heuristic_confidence": "high|medium|low",
      "status": "candidate"
    }
  ],
  "promoted": [
    {"term": "<TermName>", "promoted_at": "<ISO datetime>"}
  ],
  "dropped": [
    {"term": "<TermName>", "dropped_at": "<ISO datetime>", "reason": "<short>"}
  ]
}
```

- Same term across services → merged (locations union'd).
- Curator promotes candidates to canonical (and moves them to `promoted`) or drops them (records to `dropped` with reason).
- `dropped` entries are not re-suggested on future runs — the extractor checks against this list before proposing.

### `.last-curation.json` (marker)

```json
{
  "curated_at": "<ISO datetime>",
  "service_commits": {
    "<service-id>": "<sha>"
  },
  "term_count": 0,
  "ambiguities_resolved": 0
}
```

Used to skip re-extraction for unchanged services on the next standalone run, and to report "X new terms since last curation".

### `UBIQUITOUS_LANGUAGE.draft.md`

Same shape as the canonical file. Curator writes here during the review loop. On approve, replaces canonical and is deleted. On cancel, is deleted. On request-changes, is overwritten by the next iteration.

## Standalone Workflow `/jlu-ubiquitous-language`

`jelou/workflows/ubiquitous-language.md`, dispatched from the SKILL launcher (same pattern as `/jlu-map-codebase`).

### Step 1 — Resolve workspace

- Read `.spec-workspace.json` from CWD; resolve `WORKSPACE_PATH`.
- If missing: search up to 5 parents for `.spec-workspace/`. If still missing, error: `"/jlu-ubiquitous-language requires a .spec-workspace/. Run /jlu-map-codebase first."`
- Verify `.spec-workspace/registry/services.yaml` exists.

### Step 2 — Resolve scope

- Argument: optional `[service-id]`. If provided, scope extraction to that one service.
- If absent, scope = all services in `services.yaml`.
- Store: `SCOPED_SERVICES` (list of `{id, source_root}`).

### Step 3 — Ensure glossary directory

- Create `.spec-workspace/glossary/` if missing.
- Read existing `UBIQUITOUS_LANGUAGE.md` (if any) → `EXISTING_GLOSSARY`.
- Read `candidates.json` (if any) → `ACCUMULATED_CANDIDATES`.
- Read `.last-curation.json` (if any) → `LAST_CURATION` (per-service commit map).

### Step 4 — Determine which services need re-extraction

For each service in `SCOPED_SERVICES`:

- If `LAST_CURATION` has no entry for this service → `MUST_EXTRACT`.
- Else: `cd <source_root> && git rev-parse HEAD` → `CURRENT_SHA`.
  - If `CURRENT_SHA == LAST_CURATION.service_commits[id]` → `SKIP_EXTRACTION` (its candidates from last run are still valid; reuse from `ACCUMULATED_CANDIDATES`).
  - Else → `MUST_EXTRACT`.

Store: `SERVICES_TO_EXTRACT`.

### Step 5 — Dispatch extractor agents in parallel

- One Agent task per service in `SERVICES_TO_EXTRACT`.
- Each receives: `service-id`, `source_root`, `OUTPUT_FRAGMENT` (`.spec-workspace/glossary/.tmp/<service-id>.candidates.json`), `EXISTING_TERMS` (canonical term names + accumulated candidate term names).
- Model: `sonnet`.
- All extractor calls go in a single response (mirrors `map-codebase` Step 5).

### Step 6 — Collate candidates

- Read every fragment in `.tmp/`. Merge with `ACCUMULATED_CANDIDATES`:
  - Same term across services → union locations, evidence, `discovered_in_services`.
  - Drop entries already in `EXISTING_GLOSSARY` canonical (they don't need re-curation unless their location set changed — in which case mark for "location-only update").
  - Drop entries in `ACCUMULATED_CANDIDATES.dropped` (user-rejected previously).
- Write merged result back to `candidates.json`.
- Delete `.tmp/`.

### Step 7 — Read spec/conversation artifacts

- Glob `.spec-workspace/specs/**/SPEC.md` → `SPEC_FILES`.
- Glob `.spec-workspace/specs/**/INTERVIEW.md` (or whatever the spec-interviewer writes) → `INTERVIEW_FILES`.
- Pass file paths only to curator; curator reads them as needed.

### Step 8 — Dispatch curator agent (single, sequential)

- Inputs: `WORKSPACE_PATH`, `EXISTING_GLOSSARY` content, `candidates.json`, `SPEC_FILES`, `INTERVIEW_FILES`, scope.
- Model: `sonnet`.
- Curator runs synthesis → ambiguity detection → bounded interview → subdomain grouping → draft → review loop → atomic persist (see Curator Agent section).

### Step 9 — Report summary

```
## Ubiquitous Language Curation Complete
- Terms added: N
- Terms updated: N
- Terms removed: N
- Ambiguities resolved: N
- Services re-scanned: <list>
- Glossary: .spec-workspace/glossary/UBIQUITOUS_LANGUAGE.md
```

If user cancelled: report "Cancelled. No changes written." and exit 0.

### Workflow rules

- **Step 5 parallel dispatch is a hard requirement** — all extractor Agent calls in one response.
- **Curator owns all user interaction**; orchestrator never asks the user anything.
- **Step 4 incremental detection** reuses the marker pattern from `map-codebase` Step 4b. Re-running with no code changes makes Step 5 a no-op; Step 8 still runs to pick up unprocessed candidates from `candidates.json` (e.g., from `/jlu-map-codebase` runs since the last curation).

## Extractor Agent — `jlu-glossary-extractor`

```
agents/jlu-glossary-extractor.md
---
name: jlu-glossary-extractor
description: Scans a single service's codebase for domain terminology. Code-only, no user interview. Emits candidate terms with locations.
tools: Read, Glob, Grep, Bash
model: sonnet
---
```

### Mission

Scan one service's source code and produce a candidate-term fragment file. Code-only — never asks the user anything. Output is consumed by the curator.

### Inputs

- `service-id`
- `SOURCE_ROOT` — absolute path to the service's source code
- `OUTPUT_FRAGMENT` — absolute path to write the per-service candidate fragment
- `EXISTING_TERMS` — flat list of term names already in canonical glossary or accumulated candidates

### Behavioral guardrails

- **Never invent a definition.** Definitions are the curator's job. Extractor emits term names + locations + evidence only.
- **Skip generic programming vocabulary.** A term qualifies as "domain" only if it survives this filter:
  - **Reject** as standalone or generic suffixes: `Controller`, `Service`, `Repository`, `Module`, `Util`, `Helper`, `Manager`, `Factory`, `DTO`, `Entity`, `Model`, `Config`, `Adapter`, `Provider`, `Client`, `Handler`, `Middleware`, `Guard`, `Pipe`, `Resolver`, `Mapper`, `Builder`. (Keep them when part of a compound domain term: `AIAgentNode` is kept; `WorkflowController` reduces to `Workflow`.)
  - **Reject** generic types (`User`, `Item`, `Data`, `Record`, `Result`) only when surrounding code shows no semantic specificity.
  - **Keep**: anything that names a database table, an Elasticsearch index, an event topic, a meaningful route segment, an aggregate/entity class, an enum value representing a domain state, a workflow node type, or an integration concept.
- **Definition site vs reference site.** For each term, classify each location:
  - `definition` — the term is *defined* here (entity class declaration, table migration, type alias, OpenAPI schema, event payload schema)
  - `reference` — the term is *used* here (imported, called, referenced in a string literal)
  - First service with a `definition` becomes "Implemented in"; all others are "Also referenced by".
- **Cross-service awareness via `EXISTING_TERMS`.** If a known term is found in this service, emit a `location_updates` entry — do not re-propose it as a new candidate.
- **No subdomain grouping.** Extractor outputs flat term list; subdomains are the curator's job.

### Discovery heuristics (priority order)

1. **Schema sources** — DB migrations (`*.sql`, Prisma schema, TypeORM entities), Elasticsearch index mappings, OpenAPI/Swagger files, GraphQL schemas, protobuf files.
2. **Domain class declarations** — `*.entity.ts`, `*.aggregate.ts`, `*.model.ts`, `*.domain.ts`, `*.event.ts`, `*.command.ts`. Class names.
3. **Event/topic names** — strings passed to `eventBus.emit`, Kafka topic constants, queue/exchange names.
4. **Route segments** — beyond generic `api/v1`, segments naming resources.
5. **Enum values** — enums naming domain states (e.g., `WorkflowStatus.RUNNING`).
6. **Comments and docstrings** — only if they explicitly define a term.

### Confidence scoring

- `high` — found in ≥2 distinct evidence kinds, OR a database table name, OR an Elasticsearch index name.
- `medium` — single class declaration, single event topic, single enum.
- `low` — only seen in comments, string literals, or via heuristic naming alone.

### Output: `<OUTPUT_FRAGMENT>` JSON

```json
{
  "service_id": "<service-id>",
  "scanned_commit": "<sha>",
  "candidates": [
    {
      "term": "<TermName>",
      "evidence": [
        {"path": "src/<...>", "line": 42, "kind": "entity-class", "snippet": "<one line>"}
      ],
      "location_role": "definition|reference",
      "heuristic_confidence": "high|medium|low"
    }
  ],
  "location_updates": [
    {
      "term": "<ExistingCanonicalTerm>",
      "evidence": [{"path": "src/<...>", "line": 12, "kind": "client-import"}],
      "location_role": "reference"
    }
  ]
}
```

### Self-check before submitting

- [ ] No definitions written.
- [ ] Every term has at least one evidence entry with a real path.
- [ ] No generic programming nouns (per reject list) made it through.
- [ ] Terms in `EXISTING_TERMS` were emitted to `location_updates`, not `candidates`.

## Curator Agent — `jlu-glossary-curator`

```
agents/jlu-glossary-curator.md
---
name: jlu-glossary-curator
description: Reads candidates + existing glossary + spec artifacts, runs the user interview, drafts UBIQUITOUS_LANGUAGE.md, runs review loop, persists on approval.
tools: Read, Write, Edit, Glob, Grep, Bash, AskUserQuestion
model: sonnet
---
```

### Mission

Turn raw candidates into a curated glossary, with the user in the loop. This agent owns every interaction with the user; the orchestrator never asks questions itself.

### Inputs

- `WORKSPACE_PATH`
- `EXISTING_GLOSSARY_PATH` (may not exist on first run)
- `CANDIDATES_PATH`
- `DRAFT_PATH`
- `MARKER_PATH`
- `SPEC_FILES` — list of paths
- `INTERVIEW_FILES` — list of paths
- `SCOPED_SERVICES` — list of `{id, current_commit}` for marker bookkeeping on approval

### Behavioral guardrails

- **Never fabricate a definition.** If neither code evidence nor user interview yields a definition, emit `<PENDING — needs definition>` and surface it in the review draft. Do not invent meaning.
- **Definitions stay to one sentence.** Multi-sentence is a smell — break into multiple terms instead.
- **Aliases are *to-avoid*, not synonyms.** An alias means "the team has used this word, but going forward use the canonical term." Only list aliases backed by code evidence or user mention.
- **Free-text feedback is the contract.** During review, the user gives natural-language instructions. The agent translates them into structured edits and re-drafts. No structured forms required.
- **Atomic writes.** Canonical file is overwritten in one step on approval, after the draft is final.
- **Interview is bounded.** Maximum 5 questions across all rounds. If the user says "skip" or "good enough", stop immediately.

### Phase 1 — Synthesis (silent)

1. Read existing canonical glossary (if present) → `CANONICAL`.
2. Read `candidates.json` → `CANDIDATES` and `LOCATION_UPDATES` (collated by orchestrator Step 6).
3. Read each `SPEC_FILES` and `INTERVIEW_FILES`. Extract candidate terms from prose using the same domain-specificity filter as the extractor. Tag with `evidence.kind = "spec"` or `"interview"` and source path.
4. Compute the diff set:
   - **NEW** — candidate term not in canonical.
   - **LOCATION_CHANGED** — canonical term whose location set differs from current evidence.
   - **AMBIGUOUS** — see classes below.
   - **PENDING_DROP** — canonical term that no longer has any evidence in any scoped service.

### Phase 2 — Ambiguity detection

| Class | Trigger | Example |
|-------|---------|---------|
| **Homograph** | Same term name, evidence in two services with semantically different schema kinds | `Agent` = AI workflow node in one service AND human user role in another |
| **Synonym** | Two distinct candidate term names with overlapping evidence paths or identical schema field names | `Workflow` and `Process` reference the same UUID column |
| **Missing definition** | Term has evidence but no definition in canonical, no docstring, no spec mention | New entity class with no comments anywhere |
| **Conflicting location** | Existing canonical says "Implemented in: A" but new evidence shows a `definition` role in service B | A migration or aggregate moved to a new service |

Only these classes trigger interview questions. Everything else is auto-resolved.

### Phase 3 — User interview (only on real ambiguities)

Use `AskUserQuestion`. Maximum 5 questions, prioritized: homographs → synonyms → missing definitions → conflicting locations. Multiple-choice where possible:

- **Homograph**: present both meanings + evidence; offer `Split into two terms`, `Keep one and drop the other`, `Custom (free-text)`.
- **Synonym**: offer `Use <A> as canonical, <B> becomes alias`, `Use <B> as canonical`, `Keep both as distinct terms`, `Custom`.
- **Missing definition**: free-text answer, or `Skip — leave PENDING`.
- **Conflicting location**: `Update Implemented in to <new>`, `Keep <current>`, `Custom`.

If the user says "skip" / "all good" / "leave as is", stop interviewing immediately.

### Phase 4 — Subdomain grouping

Cluster terms by shared evidence neighborhoods (services co-occurring, modules co-occurring, schema-file co-occurring). Propose subdomain names from cluster heuristics. If genuinely ambiguous, ask one question: `Subdomain name for [<term1>, <term2>, …]?` (free text). At most one subdomain question per curation.

### Phase 5 — Draft

Write `UBIQUITOUS_LANGUAGE.draft.md` matching the canonical schema. Include:

- All canonical terms (preserved, with location updates merged in)
- All resolved candidates (now with definitions + subdomains)
- All `<PENDING — needs definition>` placeholders
- Ambiguity log with date-stamped entries for every Phase 2 ambiguity (resolved or pending), so resolution history is auditable

### Phase 6 — Review loop

Show the user a summary diff (not the full draft), then ask via `AskUserQuestion`:

```
Summary:
  + N new terms: <list>
  ~ M updated terms: <list with what changed>
  - K removed terms: <list with reason>
  ! P unresolved (PENDING definitions)
  Ambiguities resolved: <count>

Draft written to: <DRAFT_PATH>

What next?
  [Approve]   replace canonical with draft
  [Changes]   give free-text feedback; I'll re-draft
  [Cancel]    discard draft, leave canonical untouched
```

Behavior per choice:

- **Approve**: copy `DRAFT_PATH` over `EXISTING_GLOSSARY_PATH`; delete draft; update `candidates.json` (move promoted to `promoted` array; user-rejected to `dropped` with reason); write new `MARKER_PATH` with current commit map for `SCOPED_SERVICES` only (services not in scope keep their previous commit entries unchanged).
- **Changes**: prompt for free-text via `AskUserQuestion` with one open answer field. Apply changes (translate free text to structured edits — rename, redefine, merge, split, change subdomain, change location, add/remove alias). Regenerate draft. Loop back to summary.
- **Cancel**: delete draft. Do not modify canonical, candidates, or marker.

### Free-text feedback translation table

| User says | Action |
|-----------|--------|
| "Rename X to Y" | term `X` becomes `Y`; old name added to aliases-to-avoid |
| "Merge X and Y, keep X" | drop `Y`; add `Y` to `X.aliases_to_avoid`; union locations |
| "Split X into A and B" | replace `X` with two terms; if user didn't say which evidence belongs to which, ask one clarifying question |
| "Definition of X is: …" | replace `X.definition` with the supplied sentence |
| "Drop X" | move `X` to `dropped` with reason="user removed during curation" |
| "X belongs to subdomain Z" | move `X` under subdomain `Z`, creating `Z` if needed |
| "X is implemented in service S" | set `X.implemented_in = S`; reclassify other locations as references |
| "Add alias A to X" | append `A` to `X.aliases_to_avoid` |
| "Add term X with definition D in service S" | append manual term (no code evidence required, flag with `source: user`) |

Anything not parseable unambiguously: ask one clarifying question (multiple-choice if possible) before applying.

### Self-check before persisting on approval

- [ ] Every term has either a definition or `<PENDING — needs definition>`.
- [ ] Every term has at least one location row.
- [ ] Aliases-to-avoid don't include the term itself.
- [ ] Ambiguity log includes one entry per Phase 2 ambiguity.
- [ ] `candidates.json.promoted` includes every newly-canonical term.
- [ ] `candidates.json.dropped` includes every user-rejected term with a reason.
- [ ] `MARKER_PATH` reflects the commit map of `SCOPED_SERVICES` only.

## Auto-Hooks

### Hook A — `/jlu-map-codebase` (append candidates after codebase docs)

Modify `jelou/workflows/map-codebase.md`. Insert a new step between current Step 7b (write analysis marker) and Step 8 (report summary). Renumber: insert new Step 8, rename current Step 8 → Step 9.

```
Step 8 — Glossary candidate extraction (background hook)

  Precondition: .spec-workspace/glossary/ exists OR can be created.
    - If WORKSPACE_PATH is missing entirely, skip this step.
    - Otherwise create .spec-workspace/glossary/ if missing.

  Dispatch a SINGLE jlu-glossary-extractor agent (model: sonnet) for the
  just-mapped service:
    - service-id: <service-id>
    - SOURCE_ROOT: <SOURCE_ROOT>
    - OUTPUT_FRAGMENT: <WORKSPACE_PATH>/glossary/.tmp/<service-id>.candidates.json
    - EXISTING_TERMS: union of canonical term names + existing candidate names
    - MODE: "hook" — extractor logs only term names, suppresses evidence-table output

  After extractor completes:
    - Merge fragment into <WORKSPACE_PATH>/glossary/candidates.json using the same
      union logic as standalone Step 6.
    - Delete the fragment.
    - If candidates.json did not exist, create it with version=1 and empty
      promoted/dropped arrays.

  Fail-soft: if extractor errors, log a one-line warning and continue. The
  6 codebase docs are the primary deliverable; glossary is a bonus.
```

In the user-facing summary (renumbered Step 9), append:

```
### Glossary
- New candidate terms: N (run /jlu-ubiquitous-language to curate)
- Skipped: <count> (already canonical)
```

### Hook B — `/jlu-new-task` interview (read-only consultation)

> **Important context**: The `agents/jlu-spec-interviewer.md` agent is deprecated as a sub-agent (see deprecation notice in that file). Interview logic was inlined into `jelou/workflows/new-task.md` Step 14 to avoid 3-level agent nesting issues with `AskUserQuestion`. The runtime change therefore lives in the workflow file. The agent file is updated only to keep its canonical-reference documentation accurate.
>
> The companion workflow `jelou/workflows/refine-task.md` Step 8 (the refine interview) is **explicitly out of scope** for Hook B in v1 — refinement edits are narrower, and surfacing new terms there adds noise without much benefit.

Modify `jelou/workflows/new-task.md`. The change inserts a glossary-load step before Step 14a (gap analysis) and augments Step 14b (interview) and Step 14c (write spec).

```
### 14.0 — Load Canonical Glossary (read-only)

Before gap analysis (Step 14a), check for a canonical glossary:
  - Read <WORKSPACE_PATH>/glossary/UBIQUITOUS_LANGUAGE.md if it exists.
  - Extract: term names, one-sentence definitions, aliases-to-avoid.
  - Hold this as CANONICAL_TERMS for the rest of Step 14.

If the glossary does not exist, skip Step 14.0 silently. Do NOT prompt the user
to create one.
```

Interview behavior changes when `CANONICAL_TERMS` is loaded (applied within Step 14a/14b/14c):

1. **Term-suggestion (Step 14b)**: If the user says an alias-to-avoid, reflect back the canonical term, citing the glossary.
2. **Definition-anchoring (Step 14a/14b)**: Phrase clarifying questions in terms of the canonical definition.
3. **No writes**: The workflow NEVER edits `UBIQUITOUS_LANGUAGE.md`, `candidates.json`, or any glossary artifact.
4. **Surface unknown terms (Step 14c)**: If the spec or user mentions a non-generic term not in `CANONICAL_TERMS`, append it under a `## Terms introduced by this spec` section in the freshly-written `SPEC.md`. This section is read by the curator on the next standalone `/jlu-ubiquitous-language` run as part of `SPEC_FILES`. It does NOT auto-append to `candidates.json`.

Mirror the same Phase 0 / behavior-changes content into `agents/jlu-spec-interviewer.md` (the canonical reference doc) so its description matches the inlined workflow. This is a documentation update only — that agent is not invoked at runtime.

### What does NOT change

- `/jlu-execute-task`, `/jlu-create-pr`, `/jlu-close-task`, etc.: untouched. Glossary is documentation; no implementation phase reads it directly.
- `services.yaml`, `.spec-workspace.json`: untouched. Glossary lives parallel to existing artifacts.

## Edge Cases & Error Handling

| Situation | Handling |
|-----------|----------|
| `.spec-workspace/` missing when standalone command is invoked | Stop with: "Run `/jlu-map-codebase` first." |
| `services.yaml` empty | Run with empty `SCOPED_SERVICES`; curator still runs against `SPEC_FILES`/`INTERVIEW_FILES` and existing canonical |
| Extractor agent fails for one service | Continue with other services; report failure in Step 9 summary; user can re-run scoped to that service |
| Curator fails mid-draft | No canonical/candidates/marker mutation. Draft sidecar may be left behind; manual cleanup is `rm UBIQUITOUS_LANGUAGE.draft.md` |
| User cancels review | Draft deleted; canonical untouched; clean exit |
| First run (no canonical, no candidates) | Phase 1 starts from empty CANONICAL; Phase 2 ambiguities are only "missing definition" and synonym-within-candidates classes |
| Hook A run when no `WORKSPACE_PATH` resolved | Skip silently — `/jlu-map-codebase` already errored; nothing to hook into |
| Two parallel `/jlu-ubiquitous-language` invocations | Out of scope for v1. Document: "do not run concurrently." Lockfile is a future enhancement |
| Term in `CANONICAL` no longer found in any scoped service code | Surfaces as `PENDING_DROP`; curator asks user during interview (drop or keep manually-added term) |

## Testing Strategy

The plan will define test phases. The design implies these test surfaces:

- **Extractor unit tests**: against fixture services with known schemas (one with TypeORM entities, one with Prisma schema, one with raw SQL). Assert candidate output matches expected fixtures.
- **Extractor reject-list tests**: assert that generic vocabulary is filtered.
- **Orchestrator workflow tests**: incremental detection (skip-extraction path), parallel dispatch correctness, candidate merging.
- **Curator ambiguity-detection tests**: feed synthetic candidates with each ambiguity class; assert correct classification.
- **Curator review-loop tests**: simulate approve, changes (with various free-text patterns), cancel; assert filesystem state after each.
- **Hook A integration test**: run `/jlu-map-codebase` end-to-end against a fixture; assert `candidates.json` is appended; assert the run still succeeds when extractor errors.
- **Hook B integration test**: run `/jlu-new-task` Step 14 with a populated canonical glossary; assert it never writes to glossary files; assert the resulting `SPEC.md` contains a `## Terms introduced by this spec` section when the input mentions a non-canonical term; assert alias-to-avoid corrections appear in the interview reflection.

## Out of Scope (deferred)

- **Concurrency lock** for parallel `/jlu-ubiquitous-language` invocations.
- **Per-service overlay glossaries** (the original Question-2 option C). Workspace-wide only for v1.
- **Spec-reviewer terminology check** (a future hook in `jlu-spec-reviewer` that warns when a spec uses an alias-to-avoid).
- **Glossary export formats** (markdown is the only output for v1).
- **Glossary search/lookup UX** (no `/jlu-glossary lookup <term>` command).
- **Auto-PR generation** when terms change (no integration with `/jlu-create-pr`).

## Why This Shape

- **Two-agent split** matches the existing `structural` / `operational` analyzer pattern from `/jlu-map-codebase`. Familiar to readers of the plugin.
- **Tiered hooks (D)** keeps each integration point appropriately invasive: code-only contexts append candidates; user-interpretive contexts only consult.
- **Review-then-save** matches how users actually correct domain models — they react to a concrete draft. Trying to gather all the right inputs up-front would require a heavier interview that doesn't beat "show, then fix".
- **Free-text feedback** in the review loop is simpler than structured forms and matches natural language correction patterns.
- **Atomic write on approval** ensures cancel is always safe — an interrupted run never half-corrupts canonical artifacts.
- **PENDING placeholders** decouple structural completeness (the glossary has the term and its locations) from semantic completeness (a definition is supplied) — useful for incremental curation across sessions.
