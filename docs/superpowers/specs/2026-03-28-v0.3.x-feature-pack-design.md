# v0.3.x Feature Pack — Design Spec

> 6 features shipped incrementally as v0.3.1 through v0.3.6.
> Each release is independent, testable, and reversible.

---

## Overview

This spec covers 6 new capabilities for the jelou-spec-plugin, shipped as individual releases following existing plugin conventions (workflow .md, agent .md, skill launcher).

**Release order** (by dependency and value):

| Version | Feature | Type | New files | Modified files |
|---------|---------|------|-----------|----------------|
| v0.3.1 | Spec Templates | New workflow step | `jelou/templates/spec-templates/*.md`, step in `new-task.md` | `jelou/workflows/new-task.md` |
| v0.3.2 | Rollback & Recovery | New command | `jelou/workflows/rollback-phase.md`, `skills/rollback-phase/SKILL.md` | `jelou/workflows/execute-task.md` (record commit SHAs) |
| v0.3.3 | Spec Diffing & Versioning | Automatic behavior | None (inline in existing workflows) | `jelou/workflows/new-task.md`, `jelou/workflows/refine-task.md` |
| v0.3.4 | Conflict Detection | New workflow step | None (inline in existing workflow) | `jelou/workflows/new-task.md` |
| v0.3.5 | Incremental Codebase Analysis | Enhancement to existing command | None | `jelou/workflows/map-codebase.md`, `agents/jlu-codebase-analyzer-structural.md`, `agents/jlu-codebase-analyzer-operational.md` |
| v0.3.6 | PR Review Against Spec | New agent + workflow step | `agents/jlu-spec-reviewer.md` | `jelou/workflows/create-pr.md` |

**Conventions followed:**
- Workflow `.md` in `jelou/workflows/` for new commands or modifications
- Agent `.md` in `agents/` only when a new specialized agent is needed
- Skill launcher `.md` in `skills/` for new slash commands
- No new external dependencies

## Feature 1: Spec Templates (v0.3.1)

### Purpose

Reduce spec interview time by ~50% with structured starting points for common work types. Instead of discovering what type of work this is through conversation, the interviewer starts with the right questions and pre-filled sections.

### Template Registry

**Location:** `<WORKSPACE_PATH>/templates/`

Built-in templates ship with the plugin at `jelou/templates/spec-templates/` and are copied to the workspace's `templates/` directory on first use. Users can customize them or add their own.

### Built-in Templates

| Template file | Work type | Pre-filled sections | Interview focus areas |
|---|---|---|---|
| `rest-api.md` | REST API endpoint | FR: endpoint definition, request/response schema, auth. NFR: rate limits, latency. | Validation rules, error codes, pagination |
| `ui-component.md` | UI component | FR: component behavior, states, props. NFR: accessibility, responsive. | Interaction states, edge cases, design tokens |
| `db-migration.md` | Database migration | FR: schema changes, data transformation. NFR: rollback strategy, zero-downtime. Constraints: data volume. | Backwards compatibility, index strategy |
| `event-consumer.md` | Event consumer | FR: event schema, processing logic. NFR: idempotency, retry. Constraints: ordering guarantees. | Dead letter handling, concurrency |

### Template Format

```markdown
# Template: <name>

## Description
<one-line description shown in the template selector>

## Pre-filled Sections

### Problem Statement
<!-- FILL: What user need does this serve? -->

### Functional Requirements
- <pre-filled requirement placeholder specific to this work type>

### Non-Functional Requirements
- <pre-filled NFR placeholder>

### Constraints
- <type-specific constraints>

### Out of Scope
<!-- FILL: What this intentionally does NOT do -->

### Success Criteria
- <type-specific success criteria>

## Interview Hints
<!-- Guides the spec-interviewer on what to ask for this type of work -->
- <focused question area 1>
- <focused question area 2>
```

### Integration into /jlu:new-task

**New Step 2b** (after workspace resolution, before interview):

1. Scan `<WORKSPACE_PATH>/templates/` for `.md` files
2. If no templates exist yet, copy built-ins from `<PLUGIN_ROOT>/jelou/templates/spec-templates/` to `<WORKSPACE_PATH>/templates/`
3. Present AskUserQuestion with available templates + "Blank (no template)" option
4. If template selected:
   a. Seed SPEC.md with the template's pre-filled sections
   b. Pass the template's "Interview Hints" section to the spec interviewer prompt as additional context
5. Interview proceeds as normal but with a better starting point

### Custom Templates

Users create `.md` files in `<WORKSPACE_PATH>/templates/` following the same format. The system scans the directory and includes all templates in the selector. No registration needed.

## Feature 2: Rollback & Recovery (v0.3.2)

### Purpose

Provide a safe, manual escape hatch when a phase fails mid-execution. Resets the service worktree to the last known-good state.

### New Command

**`/jlu:rollback-phase <task-slug> [phase-number]`**

### New Files

- `jelou/workflows/rollback-phase.md` — workflow definition
- `skills/rollback-phase/SKILL.md` — skill launcher

### Workflow

**Step 1 — Resolve task:**
Same pattern as execute-task Step 1. Find TASK_DIR from the task slug.

**Step 2 — Read phase state:**
Read TASKS.md. Extract phase list with statuses and commit SHAs.

**Step 3 — Determine rollback target:**
- If `phase-number` is provided: target = commit SHA of the phase immediately before it (e.g., rolling back phase 3 targets phase 2's commit). For phase 1: target = the commit SHA of the worktree's HEAD before execute-task started (recorded as `pre-execution-commit` in TASKS.md when execution begins).
- If not provided: target = commit SHA of the last phase with status `done`

**Step 4 — For each affected service:**

a. Resolve worktree path (same worktree resolution algorithm as execute-task)

b. **Safety check:** Run `git status` in the worktree. If there are uncommitted changes:
   - Stop and warn: "Uncommitted changes detected in `<service-id>` worktree. Stash or commit them first: `cd <worktree-path> && git stash`"
   - Do NOT proceed.

c. **Show rollback preview** via AskUserQuestion:
   ```
   Service: <service-id>
   Current state: Phase 04 (failed after 5 retries)
   Rollback to: Phase 03 commit (<sha>)
   Files that will be reverted: <N files>

   A) Confirm rollback
   B) Abort
   ```

d. If confirmed: `git reset --hard <target-commit>` in the worktree

**Step 5 — Update TASKS.md:**
- Mark rolled-back phases as `rolled_back`
- Add rollback entry:
  ```markdown
  ### Rollback
  - Timestamp: <ISO datetime>
  - Target: Phase <NN> commit (<sha>)
  - Phases rolled back: <list>
  ```
- Set task status to `implementing` (ready for re-execution)

**Step 6 — Reset phase files:**
- For each rolled-back phase: reset the phase file's `## Execution` section
- Set status back to `pending`
- Clear Agent Output, Artifacts, and Deviations sections

### Required Change to execute-task.md

Two additions to execute-task.md:

1. **Before phase execution starts** (Step 6, transition to implementing): record the current worktree HEAD as `pre-execution-commit` in TASKS.md. This is the rollback target for phase 1.

2. **After each phase's git commit** (Step 7, after git-agent commits): record the commit SHA in TASKS.md:

```markdown
- Pre-execution commit: def5678

### Phase 01: Setup Database Schema
- Status: done
- Commit: abc1234
- Completed: 2026-03-28T10:15:00Z
```

### Safety Constraints

- Only operates on worktrees, never on main repo branches
- Refuses to run if uncommitted changes exist
- Requires explicit user confirmation showing exactly what will be reverted
- Does not delete any files outside the worktree

## Feature 3: Spec Diffing & Versioning (v0.3.3)

### Purpose

Track how specs evolve through refinements. Provides a version history and human-readable changelog showing what changed and why.

### Version Storage

```
<TASK_DIR>/
  SPEC.md                    # Current version (always latest)
  versions/
    SPEC-v1.md               # Snapshot after initial interview
    SPEC-v2.md               # Snapshot after first refine-task
    SPEC-v3.md               # Snapshot after second refine-task
    SPEC-changelog.md        # Human-readable diff summaries
```

### Automatic Versioning

**In `new-task.md`** (after interview completes and SPEC.md is written):
1. Create `<TASK_DIR>/versions/` directory
2. Copy SPEC.md to `versions/SPEC-v1.md`
3. Initialize `versions/SPEC-changelog.md`:
   ```markdown
   # Spec Changelog

   ## v1 (2026-03-28)
   Initial spec created via /jlu:new-task interview.
   Template used: <template-name or "none">
   ```

**In `refine-task.md`** (before refinement starts):
1. Read current SPEC.md content (this is the "before" state)
2. Count existing versions in `versions/` to determine next version number
3. After refinement completes:
   a. Save new SPEC.md as `versions/SPEC-v<N>.md`
   b. Compare old and new SPEC.md
   c. Generate diff entry and append to `versions/SPEC-changelog.md`:
   ```markdown
   ## v2 -> v3 (2026-03-28)
   Refined via: /jlu:refine-task "add rate limiting to the upload endpoint"

   ### Added
   - NFR: Rate limit of 100 req/min per user on upload endpoint

   ### Changed
   - FR: Upload endpoint now validates file size server-side (was client-only)

   ### Removed
   - (nothing)
   ```

### Changelog Generation

The orchestrator (during refine-task) handles changelog generation inline. It already has both the old and new SPEC.md in context. No new agent needed. The diff is structured as Added/Changed/Removed sections following a lightweight keep-a-changelog format.

### No New Command

Versioning is fully automatic. The changelog file is available for:
- Direct reading by the user
- Reference by conflict detection (feature 4) to understand what each task covers
- Inclusion in PR descriptions by the spec reviewer (feature 6)

## Feature 4: Conflict Detection (v0.3.4)

### Purpose

Detect when a new task overlaps with active tasks on the same services or files. Warn the user and require confirmation before proceeding.

### Integration Point

**New Step 5b in `new-task.md`** — after the interview completes and affected services are identified, before worktree creation.

### Detection Algorithm

**Step 1 — Scan active tasks:**
1. Read all directories under `<WORKSPACE_PATH>/specs/` (across all date folders)
2. For each directory, read `TASKS.md`
3. A task is "active" if its status is NOT `closed`, `cancelled`, or `rolled_back`
4. Exclude the current task being created

**Step 2 — Extract affected services per task:**
- From SPEC.md: look for service references in the requirements
- From PROPOSAL.md (if exists): read the affected services list directly
- From `services/` subdirectory (if exists): list service-id directories

**Step 3 — Compare with new task:**
- **Service-level overlap:** Same service-id appears in both the new task and an active task
- **File-level overlap (bonus, when available):** If the active task has a PROPOSAL.md with specific file targets in phase definitions, compare with the new task's likely file targets

**Step 4 — Report conflicts:**

If overlaps found, present via AskUserQuestion:

```
Conflict detected with active task(s):

Task: add-user-notifications (implementing, Phase 3/5)
  Overlapping services: api-gateway, notification-service
  Risk: Both tasks modify notification-service routing

Task: refactor-auth-middleware (planned)
  Overlapping services: api-gateway
  Risk: Both tasks modify auth middleware files

Options:
A) Proceed anyway (I know about these tasks)
B) Abort and review conflicts first
```

**If no overlaps:** Continue silently. No message needed.

### Performance

Filesystem scan of `<WORKSPACE_PATH>/specs/`. With 10-50 active tasks this completes in under 1 second. No database or index needed.

## Feature 5: Incremental Codebase Analysis (v0.3.5)

### Purpose

Avoid regenerating all 6 codebase docs when only a few files changed. Detect what changed since the last analysis and only re-analyze affected docs.

### Analysis Marker

After each analysis completes, write `<OUTPUT_DIR>/.last-analysis.json`:

```json
{
  "commit": "abc1234def5678",
  "timestamp": "2026-03-28T10:00:00Z",
  "docs_generated": [
    "ARCHITECTURE.md",
    "STACK.md",
    "STRUCTURE.md",
    "CONVENTIONS.md",
    "INTEGRATIONS.md",
    "CONCERNS.md"
  ]
}
```

### Modified Workflow in map-codebase.md

**New Step 4b — Detect incremental mode** (after determining source code root):

1. Check if `<OUTPUT_DIR>/.last-analysis.json` exists
2. If it exists AND all 6 docs exist in the output directory:
   a. Read the marker's commit SHA
   b. Run `git diff <last-commit>..HEAD --stat` in the service source directory
   c. If no changes: log "Codebase unchanged since last analysis. Skipping." and exit.
   d. If changes exist: categorize changed files (see below) and enter incremental mode
3. If marker or docs are missing: proceed with full analysis (current behavior)

### File Categorization Heuristic

| Changed file pattern | Affects doc |
|---|---|
| New/deleted directories, `*/routes/*`, `*/controllers/*`, entry points | ARCHITECTURE.md |
| `package.json`, `*.lock`, `go.mod`, `composer.json`, framework configs | STACK.md |
| Any new/deleted/renamed file | STRUCTURE.md |
| `.eslintrc*`, `.prettierrc*`, `tsconfig.json`, test configs | CONVENTIONS.md |
| `*/clients/*`, `*/events/*`, `*/providers/*`, `.env*`, API route files | INTEGRATIONS.md |
| Files with new TODO/FIXME/HACK comments, deprecated dependency updates | CONCERNS.md |

A single changed file can affect multiple docs (e.g., a new API client file affects both STRUCTURE.md and INTEGRATIONS.md).

### Incremental Agent Mode

When running in incremental mode, agents receive a modified prompt:

```
## Mode: Incremental Update

You are updating an existing codebase analysis document, NOT writing from scratch.

### Existing document:
<content of current doc>

### Files changed since last analysis:
<git diff --stat output filtered to relevant files>

### Detailed changes:
<git diff output for relevant files only>

### Task:
Review the changes and UPDATE the existing document. Preserve all sections that are
still accurate. Modify sections affected by the changes. Add new sections if the
changes introduce new patterns/files/integrations not previously documented.
Do NOT rewrite sections that haven't changed.
```

### Agent Dispatch Optimization

- If only STACK.md-relevant files changed: dispatch only the structural analyzer with instructions to update STACK.md only
- If only CONVENTIONS.md-relevant files changed: dispatch only the operational analyzer with instructions to update CONVENTIONS.md only
- If changes span both categories: dispatch both analyzers (same as full mode) but in incremental mode

### Modified Agent Definitions

Add an "Incremental Update Mode" section to:
- `agents/jlu-codebase-analyzer-structural.md` — covers ARCHITECTURE, STACK, STRUCTURE
- `agents/jlu-codebase-analyzer-operational.md` — covers CONVENTIONS, INTEGRATIONS, CONCERNS

The section documents: input format, update rules, what to preserve vs. rewrite.

## Feature 6: PR Review Against Spec (v0.3.6)

### Purpose

Before creating a PR, verify that the code diff actually implements what the spec requires. Detect missing requirements and scope creep. Include findings in the PR description.

### New Agent

**`agents/jlu-spec-reviewer.md`**

**Model:** MODEL_CONFIG.code (default: sonnet). This is structured comparison, not complex reasoning.

**Agent input:**
- SPEC.md (functional requirements, non-functional requirements, success criteria)
- PROPOSAL.md (phase definitions, expected changes)
- SPEC-changelog.md (if exists, for context on requirement evolution)
- `git diff` for each affected service (the actual code changes)

**Agent output:** Compliance report in structured markdown.

### Compliance Report Format

```markdown
## Spec Compliance Review

### Requirements Coverage
| Requirement | Status | Evidence |
|---|---|---|
| FR-1: Upload endpoint accepts PDF files | COVERED | upload.controller.ts:45, upload.test.ts:12 |
| FR-2: File size limit of 10MB | COVERED | upload.validator.ts:8 |
| FR-3: Return presigned URL in response | MISSING | No code found implementing presigned URL generation |
| NFR-1: Response time < 200ms | UNTESTED | Implementation exists but no performance test |

### Scope Creep Detection
| File | Change type | In spec? | Notes |
|---|---|---|---|
| notification.service.ts | Modified | No | Not mentioned in SPEC or PROPOSAL |
| package.json | New dep: @aws-sdk/s3-presigner | No | Not in STACK constraints |

### Summary
- Requirements covered: 8/10 (80%)
- Missing implementations: 2
- Untested requirements: 1
- Scope creep items: 2
```

### Integration into /jlu:create-pr

**New Step 5b** (after staging all changes, before PR creation):

1. Spawn `jlu-spec-reviewer` agent with:
   - SPEC.md, PROPOSAL.md, SPEC-changelog.md (if exists)
   - `git diff` for each service's staged changes
2. Agent returns compliance report
3. **If missing requirements found:** AskUserQuestion:
   - A) Proceed anyway (known gaps, will address in follow-up)
   - B) Abort PR creation (go implement missing requirements)
4. **If no missing requirements:** Continue to PR creation
5. Append compliance report to PR description under a collapsible section:
   ```html
   <details>
   <summary>Spec Compliance Review (8/10 requirements covered)</summary>

   [compliance report content]

   </details>
   ```

### Non-blocking

The review informs but does not block. Even with missing requirements, the user can choose to proceed. The report becomes part of the PR for human reviewers to see.

## Dependencies Between Features

```
v0.3.1 Templates ──────────────────────── (standalone)
v0.3.2 Rollback ───────────────────────── (standalone, adds commit SHA tracking to execute-task)
v0.3.3 Spec Diffing ──────────────────── (standalone)
v0.3.4 Conflict Detection ─────────────── (reads SPEC.md from other tasks; benefits from v0.3.3 changelog but works without it)
v0.3.5 Incremental Analysis ──────────── (standalone)
v0.3.6 PR Review ──────────────────────── (reads SPEC.md and PROPOSAL.md; benefits from v0.3.3 changelog but works without it)
```

No hard dependencies. The order is chosen for maximum value delivery and logical progression, not technical necessity.

## Testing Strategy

Each feature should be tested through its own `/jlu:new-task` + `/jlu:execute-task` cycle (eating our own dog food). Specific verification per feature:

| Feature | Verification method |
|---|---|
| Templates | Create a task using each template. Verify pre-filled sections appear. Verify interview focuses on template hints. |
| Rollback | Execute a task, intentionally fail a phase, run rollback, verify worktree state matches target commit. |
| Spec Diffing | Create a task, refine it twice, verify version files and changelog accuracy. |
| Conflict Detection | Create two tasks affecting the same service. Verify warning appears on the second task. |
| Incremental Analysis | Run map-codebase, modify one file, re-run. Verify only affected docs are regenerated. |
| PR Review | Create a PR for a task with intentionally missing requirements. Verify compliance report catches the gaps. |

## Out of Scope

- **Parallel phase execution across services** — Dropped per user decision. Too complex for marginal benefit.
- **Quality metrics / dashboard** — Useful but not in this feature pack.
- **Dry run mode** — Not prioritized.
- **Database or external storage** — All state remains file-based in `.spec-workspace/`.
- **New external dependencies** — Everything uses existing tools (git, filesystem, Claude Code agents).
